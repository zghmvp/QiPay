# 骑手薪资管理平台 · 架构决策纲要

> 本文是全项目的「唯一规格源」。所有开发/测试子角色必须以本文为准；与本文冲突的实现视为缺陷。
> 本文只写决策与规格，不写实现代码。术语一律中文；代码标识符英文（见 §0.3）。

## 0. 总则

### 0.1 定位
面向国内即时配送站点的「骑手薪资管理平台」：以订单明细为最小算薪单元，用公式引擎驱动差异化计薪方案，按站点/骑手结算周期出应发与实发，支持锁账、反冲补发、受控回退、骑手 H5 预支。**不做打款、不做税务、不做多级审批、不做钉钉/手机号登录。**

### 0.2 技术底座
- 后端：FBA 应用级插件 `backend/plugin/rider_salary`，`plugin.toml` 中 `[app].router=['v1']`，URL 前缀 `/api/v1/rider-salary`。
- 前端（管理后台）：FBA 前端插件 `apps/web-antdv-next/src/plugins/rider-salary`。当前 FBA 前端为 `accessMode: 'backend'`，页面出现与否由后端 `sys_menu.component`（如 `/plugins/rider-salary/views/site/index`）决定，插件 `routes/index.ts` 不驱动菜单；因此**菜单全部由插件 `sql/*/init.sql` 插入**，含 `sys_role_menu` 绑定。
- 前端（骑手 H5）：**独立轻量应用** `QiPay/rider-h5/`（Vue 3 + Vite + Vant 4 + axios），不放在 FBA 前端仓库内。原因（调研结论）：FBA 前端在不改 `src/router/routes/index.ts`、`src/router/guard.ts`、`src/store/auth.ts` 三处框架文件的情况下，无法实现「URL 直开、无侧栏、未登录进骑手登录页、按角色分流首页」。为遵守「禁止修改框架」约束，选择独立应用绕开；H5 通过同一后端 API（`/api/v1/auth/login`、`/api/v1/rider-salary/me/*`）工作，开发期用 `backend/.env` 的 `CORS_ALLOWED_ORIGINS` 追加 H5 源（`.env` 属环境配置而非框架源码）。若用户授权修改上述三处前端文件，可迁回插件目录（页面组件可复用）。
- 数据库：主验证 **PostgreSQL**；`plugin.toml` 声明 `database=['mysql','postgresql']`，`sql/mysql` 与 `sql/postgresql` 均提供（调研结论：插件表由 SQLAlchemy `create_all` 创建，`init.sql` 只负责插入菜单/角色/种子数据，两库脚本几乎一致，成本极低）。MySQL 本期不做运行验证。主键模式跟随 FBA 环境配置（自增/雪花各一份 SQL）。
- **禁止修改 FBA 框架代码**（`backend/` 除 `plugin/rider_salary` 之外的任何文件；前端除 `src/plugins/rider-salary` 之外的任何文件）。如确需修改，停止并向用户提交申请（原因、影响范围、替代方案）。
- 第三方优先：表达式求值 `simpleeval`；Excel 读写 `openpyxl`（CSV 用标准库）；节假日 `chinese-calendar`；金额 `decimal.Decimal`。以上写入插件 `requirements.txt`。若调研结论给出更优库，以调研文档为准。

### 0.3 语言约定
- 一切人可见文本（界面、字段标签、提示、报错、日志、导出表头、API 的 `summary/description`、Pydantic `description`、SQL `COMMENT`）**全部中文，不做国际化**，前端不使用 `$t()`/langs，直接写中文。
- 代码标识符（表名、列名、变量、函数、路由 path、权限码）用英文 snake_case/kebab-case，保证与 FBA/SQLAlchemy/工具链兼容。
- **公式引擎变量名与运算符使用中文**（如 `配送距离 > 5 且 送达时刻 在时段内 ["22:00","06:00"]`），使计算过程对业务人员可读。

### 0.4 命名
- 表前缀 `rs_`；权限码前缀 `rs:`；菜单目录名「骑手薪资」；前端路由前缀 `/rider-salary`，H5 前缀 `/rider-h5`。
- 金额 `Numeric(12,2)`；距离（公里）`Numeric(8,2)`；重量（斤）`Numeric(8,2)`；单价 `Numeric(10,4)`。
- 业务日期 `biz_date: date`；时间戳按 FBA 时区工具。

### 1.5 方案绑定 `rs_rider_plan_binding`
| 列 | 含义 | 约束 |
|---|---|---|
| rider_id | 骑手 | |
| plan_version_id | 方案版本 | 只能绑定状态=启用 的版本 |
| binding_type | 绑定类型 | enum: `default`默认 / `override`区间覆盖 |
| start_date / end_date | 生效区间 | default 允许 end_date 空；override 必填两端 |

**生效方案解析规则**（同一天只能一个生效方案）：某日 d 的生效方案 = 覆盖 d 的 override（override 之间禁止重叠，保存时校验）；若无，则取覆盖 d 的 default（default 之间禁止重叠）；都无 → 该日「无方案」，算薪时该日订单记为「未计薪-无方案」并在日历上以警示状态显示。

### 1.11 导入批次 `rs_import_batch`
`site_id, file_name, total_rows, success_rows, failed_rows, status(处理中/成功/部分失败/失败), date_from, date_to（本批覆盖的业务日期范围）, error_report JSON（行号+原因，中文）, operator_id, remark`。
「未导入日」判定：站点在该日期无任何批次覆盖且无任何订单（含补录）。「无数据日」= 有覆盖但该骑手 0 单。

### 1.12 奖惩记录 `rs_adjustment`（手工录入，统一结构）
`rider_id, site_id(快照), biz_date, subject_id, amount(正数；符号由科目方向决定，「上期补差」允许负数), signed_amount(计算列), remark(必填), period_id(算薪时回填), is_locked, operator_id`。
- 录入粒度：骑手 + 日期 + 科目 + 金额 + 备注，一条一行。奖与惩共用同一页面与结构。
- 「按周期入账」的科目录入时 biz_date 取周期内任意日（默认周期首日），日历按 biz_date 展示。

### 1.13 结算周期 `rs_settle_period`
| 列 | 含义 | 说明 |
|---|---|---|
| site_id | 站点 | |
| rider_id | 骑手 | **NOT NULL DEFAULT 0**；0 表示站点级周期，非 0 表示该骑手的个性化周期（覆盖站点） |
| cycle_type | 周期类型 | |
| start_date / end_date | 区间 | 唯一(site_id, rider_id, start_date) |
| status | 状态 | enum: `open`开放 / `locked`已锁账 / `paid`已发薪 / `reopened`补发中 |
| locked_by/locked_time, paid_by/paid_time, reopened_by/reopened_time | | |
| remark | | |

周期实例按需生成（首次算薪或手动「生成周期」）。骑手若有周期覆盖，则其结果归入 rider 级周期，站点级周期算薪时跳过该骑手。

**周期状态机**
```
open ──锁账──▶ locked ──标记发薪──▶ paid
locked ──反冲补发──▶ reopened          paid ──反冲补发──▶ reopened
reopened ──再次锁账──▶ locked
```
- 锁账：该周期内 `rs_order`/`rs_adjustment` 置 `is_locked=true`；所有 `rs_payroll` 状态 draft→finalized；引用的方案版本 `is_used=true`。
- 反冲补发（locked/paid → reopened）：为每个 finalized/paid 的 payroll 生成一条 `kind=reversal` 的镜像负单；原单标记 `reversed=true`；解除 is_locked；此后修改数据、重算时生成 `kind=supplement` 补发单（全额重算），导出时展示 原单 / 反冲 / 补发 三行与净差。**不提供「直接解锁」。**
- 已发薪(paid) 只是标记，不涉及付款。

### 1.15 薪资明细 `rs_payroll_detail`
`payroll_id, rider_id, biz_date(周期项可空), stage, plan_version_id(可空), plan_item_id(可空), subject_id, order_id(可空), amount(带符号), include_in_gross, source(enum: formula公式/manual手工/advance预支抵扣/reversal反冲), calc_trace JSON`。

### 1.17 预支单 `rs_advance`
| 列 | 含义 |
|---|---|
| rider_id / site_id | |
| amount | 预支金额 |
| reason | 原因（必填） |
| status | enum: `draft`草稿 / `pending`待审核 / `rejected`已驳回 / `to_pay`待发放 / `paid`已发放 / `cancelled`已取消 |
| approver_id / approve_time / approve_remark | 审核 |
| paid_by / paid_time | 发放标记（导出打款明细后由管理员标记） |
| deducted_amount / remaining_amount | 已抵扣 / 待抵扣 |
| deduct_status | enum: 未抵扣/部分抵扣/已抵扣 |
| submit_time / cancel_time | |

**状态机**
```
draft ──提交──▶ pending ──审核通过──▶ to_pay ──标记已发放──▶ paid
draft/pending ──骑手撤回──▶ cancelled
pending ──驳回──▶ rejected
to_pay ──管理员取消──▶ cancelled
paid：发薪时自动抵扣 → deduct_status 变化；remaining_amount>0 结转下期
```
约束：
- 同一骑手同时最多一笔 status ∈ {pending, to_pay}。
- 上限 = rider.advance_limit ?? site.advance_limit ?? 全局设置 `RIDER_SALARY_ADVANCE_LIMIT_DEFAULT`（plugin.toml [settings]，默认 3000）。超限拒绝提交。
- 审核权限：该站点 owner/deputy、薪资管理员、超级管理员。
- 抵扣：算薪时按 paid 且 remaining_amount>0 的预支单，按 paid_time 先后抵扣，抵扣额 = min(remaining, 应发−代扣)，多退少补（差额结转）。
- 只导出预支明细，不打款。

### 1.18 站点公告 `rs_notice`
`site_id(可空=全部站点), title, content, publisher_id, publish_time, status(草稿/已发布/已下线)`。骑手端只看本站点 + 全部站点的已发布公告。

### 1.19 业务审计日志 `rs_audit_log`
`operator_id, operator_name(快照), operate_time, module(模块), action(动作), target_type, target_id, target_label(对象摘要), reason(原因), before JSON, after JSON, description(自然语言中文一句话), ip, trace_id`。
- 每个写操作必写；`reason` 在以下动作**必填**：订单纠错、奖惩修改/删除、锁账、反冲补发、方案停用、方案回退、预支驳回/取消、开通/停用骑手账号。
- `description` 模板：「{操作人} 于 {时间} 对 {对象} 执行了 {动作}，原因：{原因}」。
- FBA 自带操作日志（接口级）照常记录，作为技术审计补充；业务追溯以本表为准。

### 2.2 触发条件（结构化 JSON → 编译为表达式）
```json
{"逻辑":"且","条件":[
  {"字段":"送达时刻","运算符":"在时段内","值":["22:00","06:00"]},
  {"字段":"配送距离","运算符":">","值":5},
  {"逻辑":"或","条件":[
    {"字段":"是否节假日","运算符":"=","值":true},
    {"字段":"是否恶劣天气","运算符":"=","值":true}
  ]}
]}
```
- 运算符：`=`、`≠`、`>`、`≥`、`<`、`≤`、`在区间内`[a,b]（含端点）、`不在区间内`、`在时段内`[起,止]（支持跨午夜）、`属于`[枚举…]、`不属于`。
- 逻辑：`且`、`或`、`非`；最多嵌套 2 层。
- 空条件 = 恒真。
- 编译：后端将 JSON 编译为 Python 表达式字符串（中文变量名），交 `simpleeval` 求值；`在时段内` 等编译为白名单函数调用 `在时段内(送达时刻, "22:00", "06:00")`。字段与运算符类型不匹配 → 保存时报中文错误。

### 2.3 计算公式（模板式 JSON）
| 类型 | JSON 示例 | 语义 |
|---|---|---|
| 固定金额 | `{"类型":"固定金额","金额":2}` | 每次命中加 2 元 |
| 字段乘单价 | `{"类型":"字段乘单价","字段":"配送距离","单价":0.8,"起算值":5}` | (字段 − 起算值) × 单价，结果<0 取 0 |
| 阶梯 | `{"类型":"阶梯","字段":"周期单量","模式":"全量落档","计价":"按单价","档位":[{"下限":0,"上限":300,"值":5},{"下限":300,"上限":600,"值":5.5},{"下限":600,"上限":null,"值":6}]}` | 全量落档：找到 字段 所在档，金额 = 字段 × 值（计价=按单价）或 = 值（计价=固定金额）；分段累进：Σ 每档 (min(字段,上限)−下限) × 值 |
| 表达式 | `{"类型":"表达式","表达式":"最大值(0, 3000 - 本期已计金额)"}` | 由前端表达式拼装器生成的中文表达式；允许字段、数字、`+ - * /`、括号、函数 `最大值/最小值/取整/向上取整/四舍五入/绝对值` |

- 距离阶梯/重量阶梯 = 逐单阶段、字段=配送距离/商品重量、计价=固定金额。
- 单量阶梯 = 周期阶段、字段=周期单量 或 方案期内单量、模式可选全量落档/分段累进。
- 底薪 = 周期阶段、固定金额（跨段分摊由方案作者选表达式 `底薪 × 方案生效天数 / 周期天数`；引擎提供「底薪分摊」快捷模板生成该表达式）。
- **底薪+单量阶梯（单方案）** = 同一版本内同时配置周期底薪项 + 周期阶梯项（见 `04-薪资方案案例库.md` C03/C04）；与「月中换绑定到纯阶梯方案」不同。
- 保底 = 周期阶段、表达式 `最大值(0, 保底金额 − 本期已计金额)`，排序置最后。
- 金额按项四舍五入到 2 位（`ROUND_HALF_UP`），再汇总。

### 2.4 试算
- `POST /plan-versions/{id}/trial`（或对未保存草稿 `POST /plan-versions/trial` 传完整 items）：入参 `rider_id`、`start_date`、`end_date`（或 `order_ids`）；引擎以「假定该版本在区间内全程生效」在内存中运行完整流水线，**不落库**；返回逐单明细、按日汇总、周期项、应发/实发，以及每条明细的 `calc_trace`。
- 试算成功后回写 `trial_hash`（items 内容哈希）与 `trial_snapshot`；**启用**要求 `trial_passed && trial_hash == 当前哈希`，否则报「方案内容已变更，请重新试算」。

### 2.5 版本生命周期
```
draft ──试算通过后「启用」──▶ active ──「停用」──▶ disabled
active/disabled（is_used=true）──「复制为新版本」──▶ 新 draft(version_no+1, copied_from)
active/disabled ──「回退」(仅超管)──▶ voided（见 §4.5）
draft（未使用）可编辑、可删除
```

## 3. 算薪引擎流水线（伪代码级规格）

```
计算骑手周期薪资(rider, period, 模式=正式|试算):
  payroll = 获取或新建 draft payroll(period, rider, kind=normal 或 supplement(若 period.status==reopened))
  若 payroll.status ∉ {draft} → 拒绝（「已定稿结果不可重算，请走反冲补发」）
  清空 payroll 旧明细
  段列表 = 解析绑定(rider, period.start, period.end)      # [(plan_version, 段起, 段止)]，按日拆，连续同版本合并
  周期上下文 = 聚合(周期单量, 周期有效单量, 周期天数, 出勤天数, 工龄月数, 入职天数, 手工奖惩合计…)
  已计金额 = 0
  for 段 in 段列表:
    for 日 in 段.日期序列:
      日上下文 = {日期, 星期, 是否节假日(chinese-calendar), 是否周末, 日标记(rs_day_flag), 用工类型(按日)}
      订单 = 有效订单(rider, 日)
      for 订单 in 订单:
        上下文 = 订单字段 ∪ 日上下文 ∪ 骑手字段
        for 项 in 段.版本.逐单项(按 sort_order):
          if 求值(项.condition_expr, 上下文):
            金额 = 求值(项.formula_expr, 上下文) × 方向符号
            写明细(stage=逐单, order_id, calc_trace); 若 include_in_gross: 已计金额 += 金额
      日聚合 = {日单量, 日有效单量, 日逐单金额}
      for 项 in 段.版本.按日项: 同上，写明细(stage=按日, biz_date)
      刷新 rs_payroll_daily(rider, 日)
    段上下文 = 周期上下文 ∪ {方案期内单量, 方案生效天数, 本期已计金额=已计金额, 本期逐单金额…}
    for 项 in 段.版本.周期项(按 sort_order):
      if 求值(条件): 金额 = 求值(公式, 段上下文); 写明细(stage=周期, plan_version_id=段.版本); 已计金额 += …
  无方案日 = 周期内未被任何段覆盖且有有效订单的日期 → rs_payroll_daily.day_status = 无方案，并在 payroll.warnings 记录
  手工奖惩 = rs_adjustment(rider, biz_date ∈ period, 未锁或属本周期) → 逐条写明细(source=手工)，回填 adjustment.period_id
  gross = Σ(include_in_gross 明细)
  deduction_total = Σ(¬include_in_gross ∧ 方向=惩 的 |明细|)
  advance_deduction = 抵扣预支(rider, 可抵扣额=max(0, gross − deduction_total))   # 试算模式不抵扣、不落库
  net = gross − deduction_total − advance_deduction
  payroll.calc_version += 1; stale=false; 保存
  写审计日志(「重算」, 无需 reason)
```
跨段规则：
- 「周期单量」永远是骑手整个周期的单量；「方案期内单量」只统计本段。方案作者决定单量阶梯用哪一个。
- 每个段的周期项独立执行一次，明细带 `plan_version_id`；「底薪」若不做分摊表达式，则两段各计一次全额（引擎不擅自分摊，由试算暴露问题）。
- 「本期已计金额」跨段累计。

反冲单生成：`kind=reversal` 的 payroll 复制原单所有明细并取负；`reversed_of_id` 指向原单；状态直接 finalized；原单 `reversed=true`（新增 bool 列）。

## 4. 关键流程

### 4.1 订单导入
1. 下载模板（xlsx，中文表头：站点编码、骑手工号、订单号、配送距离(公里)、商品重量(斤)、下单时间、送达时间、订单状态、订单金额、备注）。
2. 上传 → 后端 `openpyxl`/`csv` 解析 → 逐行校验（站点存在、骑手存在且属该站点、订单号唯一、时间格式、状态枚举、所属周期未锁账）→ 全部合法才入库（默认「整批事务」，可选「跳过错误行」参数）→ 生成批次与错误报告（中文行级原因，可下载）。
3. 入库后标记受影响 (rider, biz_date) 所在 draft payroll `stale=true`；可选参数 `auto_recalc=true` 时在 BackgroundTasks 中重算。
4. 单条补录 `POST /orders`、纠错 `PUT /orders/{id}`（必填 reason）、删除 `DELETE`（必填 reason，锁账拒绝）。

### 4.2 锁账
`POST /periods/{id}/lock` 必填 reason。前置：所有 draft payroll 不 stale（否则提示先重算）。动作见 §1.13。

### 4.3 导出
`GET /periods/{id}/export` → xlsx：汇总表（工号、姓名、站点、周期、单量、逐单、按日、周期项、奖、惩、应发、代扣、预支抵扣、实发、状态、kind）+ 明细表 + 奖惩表。`GET /advances/export` → 预支明细。

### 4.4 重算标记
任何对 `rs_order` / `rs_adjustment` / `rs_rider_plan_binding` / `rs_day_flag` / `rs_rider_employ_history` 的写操作，服务层统一调用 `mark_stale(rider_ids, date_range)`：找到覆盖的 open/reopened 周期的 draft payroll 置 `stale=true`（无 payroll 则不动）。工作台/周期列表突出显示「需重算」。

### 4.5 受控回退（仅超级管理员）
1. `GET /plan-versions/{id}/rollback-preview` 返回：受影响绑定数、受影响 payroll（按周期/骑手，区分 draft / finalized / paid）、将作废的版本、将触发的反冲单数量、将被解绑的骑手清单。
2. 前端弹窗完整列出后果；若存在 paid → 额外明示「该方案已执行发薪操作，回退将产生财务影响」，要求输入确认文字「确认回退」。
3. `POST /plan-versions/{id}/rollback` 入参 `reason`（必填）、`confirm_text`。后端：
   - 版本 → voided；其所有绑定 → 删除（写审计）；
   - 引用它的 draft payroll → voided，并对其 (rider, period) 置需重算标记；
   - 引用它的 finalized/paid payroll → 生成反冲单（§3），原单 `reversed=true`，所属周期 → reopened；
   - 自动复制一份新 draft（copied_from=被回退版本），供修改后重新试算启用；
   - 审计日志 description 必须含后果摘要。
4. 未定稿（全部 draft）的回退不弹财务警告，但仍需 reason。

### 4.6 骑手账号
`POST /riders/{id}/open-account`：用 FBA 用户 CRUD 创建 `sys_user`（username=工号，初始密码=手机后 6 位或指定，nickname=姓名，`is_staff=False`，`is_superuser=False`），绑定「骑手」角色（该角色**不绑定任何菜单**），回写 `rider.user_id`。`POST /riders/{id}/reset-password`、`/disable-account`。
- 骑手端所有接口 `/me/*` **只用 `DependsJwtAuth`**（不使用 `DependsRBAC`，因为 FBA 的 RBAC 依赖会拒绝非 `is_staff` 用户的写操作，且要求角色绑定菜单），再叠加插件内依赖 `DependsCurrentRider`：`request.user.id → rs_rider.user_id`，找不到或骑手已离职 → 403「当前账号不是有效骑手账号」。
- 管理端接口一律 `DependsJwtAuth + DependsRBAC + RequestPermission('rs:...')`，骑手账号因无菜单权限自然被拒。
- 骑手账号若误登录管理后台，菜单为空，属预期。

## 5. 权限

FBA 角色（init.sql 预置；用户可在 FBA 角色管理里调整）：
| 角色 | 说明 | 数据范围 |
|---|---|---|
| 超级管理员（FBA 内置 superuser） | 全部，含回退 | 全部站点 |

| 站点副负责人 `rs_site_deputy` | 同负责人 | 同上 |
| 骑手 `rs_rider` | 仅 `/me/*` | 本人 |

- 站点数据范围在 **Service 层**统一过滤：`可见站点(user) = 全部（超管/rs_admin）| rs_site_manager 中的 site_id`。调研结论：FBA 数据权限基于部门规则，无「部门及下级」自动展开且无规则时结果为空，对「站点负责人」场景收益小、易误判，**本期不使用 FBA 数据权限**，只复用其角色-菜单 RBAC。
- FBA 的 RBAC 依赖对非超管有三条硬规则（调研）：必须有启用角色且角色绑定了菜单；非 GET 请求要求 `is_staff=True`；权限码必须落在角色菜单 `perms` 中。因此 init.sql 必须：为 4 个后台角色插入 `sys_role` + `sys_role_menu`；管理类账号由管理员在 FBA 用户管理中勾选「后台管理(is_staff)」。
- 逻辑删除：FBA 的 `deleted` 列值为行 id 而非 1；插件查询若用到带逻辑删除的 FBA 表（sys_user/sys_role），一律加 `deleted=0`。

## 8. 边界与异常（实现必须覆盖）
- 导入：订单号重复（同批/库内）、骑手不在该站点、送达早于下单、状态非法、目标周期已锁账、空文件/表头不符 → 中文行级报错；导入不产生半成品（整批事务）。
- 算薪：某日无生效方案 → 该日订单不计薪并标记「无方案」；方案项条件字段在该阶段不可用 → 保存即报错；除零/空值 → 视为 0 并记 warning；阶梯档位重叠/不连续 → 保存报错。
- 绑定：区间重叠、绑定非启用版本、结束早于开始 → 拒绝。
- 锁账：存在 stale payroll → 拒绝并列出；周期无任何 payroll → 允许锁（空周期）。
- 预支：重复待处理单、超限、非本站点负责人审批 → 拒绝；骑手离职 → 禁止申请。
- 回退：非超管 403；未输入确认文字 → 拒绝；版本 draft 未使用 → 提示直接删除即可。
- 科目删除：被引用 → 拒绝并返回引用计数。
- 骑手离职后：不再算薪（leave_date 之后订单标记异常）；历史可查。
- 跨周期订单：biz_date 决定周期，导入到已锁周期 → 拒绝并提示走反冲补发。
