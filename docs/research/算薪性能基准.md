# P5-12 算薪性能基准

Q-19 采用计划第 12 节的推荐规模，没有另做拍板。这次只跑内存里的小样本，**没有往共享库 `fba` 写任何订单或骑手**。计划里的 nightly CI 这次不做。

## 目标规模（Q-19 推荐）

| 项 | 规模 |
|---|---|
| 站点 | 20 |
| 骑手 | 2000（大约每站 100 人） |
| 日订单 | 6 万 |
| 保留 | 2 年 |

2 年订单大约是 `60000 × 365 × 2 ≈ 4380 万` 行。这个量只应落在专用库，不要灌进 `fba`。

## 这次实际跑的规模

| 项 | 取值 |
|---|---|
| 站点 | 1 |
| 骑手 | 2 |
| 订单 | 48（每人 24 张，3 天，每天 8 张，其中 4 张夜间） |
| 方案 | 逐单（基础单价、夜间补贴、距离补贴）、按日（日单奖）、周期（底薪、阶梯提成） |
| 重复 | 算薪 5 次，取中位数 |
| 环境 | 进程内调用现有函数。列表和导出用记录语句的假会话，不连 PostgreSQL |

入口：`fastapi-best-architecture/backend/plugin/rider_salary/tests/test_perf_benchmark.py`

```bash
cd fastapi-best-architecture
uv run ruff check --no-fix backend/plugin/rider_salary/tests/test_perf_benchmark.py
uv run --python 3.12 pytest backend/plugin/rider_salary/tests/test_perf_benchmark.py -q -s
```

算薪走 `run_calc_pipeline`（纯内存，不含 Redis 锁和落库）。列表走 `order_service.get_list` 与 `payroll_service.get_list`。导出走 `order_service.export`，并单独消费 `export_service._iter_detail_rows`。

## 测到的数字

本机一次结果（2026-10-09，会随机器浮动，阈值只挡数量级回退）：

| 指标 | 结果 | 阈值 |
|---|---|---|
| 算薪中位数 | **10.61 ms** / 48 单（约 **4526 单/秒**） | < 2000 ms |
| 订单列表语句数 | 页大小 20 与 40 都是 **5** 次，较慢一次 **6.18 ms** | 两次相等，且 ≤ 6 |
| 薪资单列表语句数 | 页大小 20 与 40 都是 **2** 次，较慢一次 **2.52 ms** | 两次相等，且 ≤ 6 |
| 订单导出 | **流式**。`write_only=True`，`yield_per=500`，第一行数据写入时只拉过 1 笔订单。48 单 **13.55 ms** | < 2000 ms |
| 周期薪资明细 | **流式**。同样 `yield_per=500`，24 行 **6.28 ms** | < 2000 ms |

订单列表的 5 次语句是：计数、分页、按主键再取订单、批量取骑手、批量取站点。后一次取订单是因为 `paging_data` 先 `model_dump()`，行变成字典，`_to_details` 再按 id 装回模型。页从 20 增到 40 时次数不变，不是按行 N+1。

薪资单列表只有计数和分页，服务本身不再补查询。

订单导出和薪资明细行都走 `StreamingWorkbook`（openpyxl `write_only`）加 `stream` / `yield_per`。表头写入时订单还没开始拉；第一行数据写入时只消费了 1 笔。

## 以后全量怎么跑

1. 单独建库，库名不要用 `fba`。执行前用 `psql -c 'select current_database()'` 确认。Redis 用非 0 号库。
2. 按 Q-19 灌数：20 站、2000 骑手、每天 6 万单。先灌 1 天验证，再决定是否灌满 2 年（约 4380 万订单）。灌数脚本放 `/tmp`，不要留在仓库，也不要指向开发库。
3. 在那套库上测三件事，并和这次的小样本对照：
   - 一个开放周期、约 100 名骑手的算薪耗时（含锁和落库），换算成单/秒。
   - 订单列表、薪资单列表在页大小 20 下的语句数，以及数据库侧 P95。语句数仍应接近这次的 5 和 2，不随页内行数线性涨。
   - 导出 1 天订单（约 6 万行，已超过当前 5 万行上限，预期直接拒绝）和未超限的一批明细，确认仍是 `write_only` + `yield_per`，进程内存不随导出行数线性涨。
4. 只想加大内存算薪、仍然不碰数据库时，改测试文件顶部的 `RIDER_COUNT` 和 `ORDERS_PER_RIDER` 再跑同一条 pytest。这测的是公式流水线，代替不了数据库 P95。
5. 计划写了把基准放进 nightly CI。这次按派遣不改 CI。全量库稳定之后，再单独加一条不跑在默认 `pytest` 里的夜间任务。

## 已知限制

- 数字不含 PostgreSQL、Redis 锁、草稿落库和预支抵扣写库，不能当成 Q-19 的吞吐承诺。
- `export_period` 的薪资单头仍先 `list()` 进内存，明细和奖惩行才流式写出。这次测到的是明细迭代器和订单导出。
- 阈值写在测试常量 `CALC_MEDIAN_MS_MAX`、`LIST_QUERY_MAX`、`LIST_ELAPSED_MS_MAX`、`EXPORT_ELAPSED_MS_MAX`。
